## gather-info スキルの自動実行

以下の条件で gather-info スキルを自動的に使用してください:

### 自動実行トリガー

- 新機能の実装を依頼された時
- 「〜を作って」「〜を実装して」など実装タスクの依頼
- タスクの説明が曖昧で、実装に必要な情報が不足している場合
- 複数のアプローチが考えられ、選択基準が不明確な場合

### スキップ条件

- ユーザーが明確に「質問せずに進めて」と指示した場合
- 既に仕様ドキュメントが提供されている場合
- 非常に単純なタスク (例: typo修正、1行の変更)
- デバッグや調査のみを依頼された場合

### 出力先

- 大規模タスク: `<project>/docs/specs/<task-name>-spec.md`
- 小規模タスク: Plan Mode で使用される `.claude/plans/` 内のファイル

## タスク管理ツールの積極活用

作業の進捗を可視化し、複合的なタスクを構造的に管理するため、TaskCreate / TaskList / TaskUpdate を積極的に活用してください。

### 自動実行トリガー

- 3ステップ以上の複合的な作業を依頼された時
- 複数ファイルにまたがる変更が必要な時
- ユーザーが複数の要求を一度に伝えた時
- Plan Mode で計画を立てた後、実行に移る時

### スキップ条件

- 単一の簡単な操作（typo修正、1ファイルの小さな変更）
- 質問への回答や調査のみの依頼
- 会話的なやり取り

### ステータス管理フロー

1. TaskCreate で `pending` 状態のタスクを作成（`activeForm` を必ず設定）
2. 作業開始時に TaskUpdate で `in_progress` に更新
3. 作業完了時に `completed` に更新
4. TaskList で次のタスクを確認

### 依存関係

- タスク間に順序依存がある場合は `addBlocks` / `addBlockedBy` を設定する
- ブロックされているタスクには着手しない

### タスク作成の原則

- subject: 命令形で簡潔に（例: 「ログイン機能のバグを修正する」）
- activeForm: 現在進行形（例: 「ログイン機能のバグを修正中」）
- description: 他のエージェントが読んでも理解できる詳細を含める
